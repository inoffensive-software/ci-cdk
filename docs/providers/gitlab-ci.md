# GitLab CI

## Scope

The provider behind the `@inoffensive/ci-cdk/gitlab-ci` subpath export, built from `src/gitlab-ci/`
to `dist/gitlab-ci/`. It emits the `.gitlab-ci.yml` a repository keeps at its root.

It owns `index.ts` (the barrel), `render.ts`, `types.ts`, `runtime-types.ts`, `blocks.ts`,
`runtime-blocks.ts`, `delivery-blocks.ts`, `trigger-types.ts`, `leaves.ts`, `to-doc.ts`,
`validate.ts`, their colocated tests and the goldens in `src/gitlab-ci/__snapshots__/`. The layers,
the public surface and the emitted format are described once in
[`docs/architecture.md`](../architecture.md); this file does not repeat them.

## Coverage

The claim is the corpus, and the corpus is asserted by these tests:

- [`terraform-images.test.ts`](../../test/corpus/gitlab-ci/terraform-images.test.ts),
  [`labkit.test.ts`](../../test/corpus/gitlab-ci/labkit.test.ts),
  [`gitlab-pages.test.ts`](../../test/corpus/gitlab-ci/gitlab-pages.test.ts),
  [`gitlab-pages-job.test.ts`](../../test/corpus/gitlab-ci/gitlab-pages-job.test.ts),
  [`gitlab-run.test.ts`](../../test/corpus/gitlab-ci/gitlab-run.test.ts) and
  [`gitlab-secrets.test.ts`](../../test/corpus/gitlab-ci/gitlab-secrets.test.ts) and
  [`gitlab-tokens.test.ts`](../../test/corpus/gitlab-ci/gitlab-tokens.test.ts) render each entry and
  compare it with the pinned file as parsed data.
- [`exhaustiveness.test.ts`](../../test/corpus/gitlab-ci/exhaustiveness.test.ts) holds the modelled
  set to the corpus keys and the ledger in both directions, and fails when a modelled key is written
  through `raw` or a ledger row is unused.
- [`coverage.test.ts`](../../test/corpus/gitlab-ci/coverage.test.ts) holds the ledger to the
  fixtures' `raw` usage, and asserts the ledger is empty.
- [`schema-gap.test.ts`](../../test/corpus/gitlab-ci/schema-gap.test.ts) holds the modelled set and
  the pinned schema to each other in both directions.

The table below is generated from the inventory's modelled key paths and the entries' corpus paths by
`test/corpus/gitlab-ci/coverage-table.ts`. GitLab mixes pipeline keywords with job names at the
document root, which the gate normalises to `$.*`, so a job keyword is modelled once and shown once.
`document.test.ts` compares the block with this file, so editing it by hand fails.

## Documented grammar

[`docs/references/upstream-schemas.md`](../references/upstream-schemas.md) pins the schema this section
reads as a grammar: a gap is a schema path the provider cannot emit, and an overclaim is a modelled
path the schema rejects. `test/corpus/gitlab-ci/documented-grammar.ts` generates the block below from
the walker's paths, `GAPS` and `OVERCLAIMS`; `document.test.ts` compares it with this file, so editing
it by hand fails. The gate and its refresh rule are in
[ADR 0011](../decisions/0011-documented-grammar-gate.md).

Every gap is listed once, in its category: `unmodelled` is debt the provider could pay, `out-of-scope`
is a shape the non-goals below name, and `schema-noise` is grammar the schema permits and GitLab does
not document. The counts are computed from the lists, never written by hand.

## Quirks

- **Keywords and job names share the root.** A named key is a pipeline keyword; any other key is a job
  the author named. The gate normalises the second to `$.*`, and the coverage table shows each job
  keyword once rather than once per job.
- **`!reference` is a leaf, not a string.** A plain string would be quoted and read as a command, so
  `ref([".setup", "script"])` emits a tagged sequence. The tag is emit-only: the path is never
  resolved, and the pinned corpus loses it because the `yaml` parser drops an unknown tag, as
  `PROVENANCE.md` records. See [ADR 0016](../decisions/0016-gitlab-reference-leaf.md).
- **A job's `script` is optional.** A fragment may inherit one through `extends` or an `include`, and
  an omitted `stage` is not checked against `stages`, because a merge may supply either. See
  [ADR 0014](../decisions/0014-job-script-is-optional.md).
- **Hidden templates are author data.** A top-level `.`-prefixed key belongs in `templates`, is
  emitted in record order and never validated or counted as grammar, on either the modelled or the
  documented side.
- **`trigger` names a `branch`, not a `ref`.** A project trigger takes `branch`; only `include` and
  `release` carry `ref`.
- **The corpus compares data, not bytes.** Key order, quoting, block versus flow collections, blank
  lines and comments are outside the claim; values, nesting and scalar types are inside it. See
  [ADR 0005](../decisions/0005-corpus-compares-data.md) and
  [ADR 0007](../decisions/0007-corpus-compares-data-only.md).
- **A string that spells a number stays a string.** `STABLE_VERSION: "1.5"` emits `"1.5"`, so it
  parses back as text. See [ADR 0010](../decisions/0010-string-and-number-are-distinct-at-the-boundary.md).
- **`run` replaces `script`, it does not join it.** A job may declare a step list or a `script`, never
  both; `validate` names both paths when it sees the pair. The step list is emitted between `script`
  and `after_script`. See [ADR 0017](../decisions/0017-run-steps-replace-script.md).

## Non-goals

- Resolving `include`, `extends` or `!reference`. They are emitted, never loaded or verified.
- A `spec` header, inputs interpolation and component context (`$[[ ... ]]`); `include:inputs` is
  passed through as data only.
- Child pipelines and multi-document pipelines as a composition mechanism. `trigger:include` is
  emitted as data and never run.
- `rules:changes:compare_to`, deferred to spec 0009.
- A CLI or file-writing behaviour; `render` still returns text.
- Refreshing the vendored schema, and modelling any declared `GAPS` row. Triage classifies; a row
  becomes vocabulary only when a pinned corpus entry already needs it.

Keys outside the vocabulary can still be written through `raw` where a struct exposes it; a corpus
key that needs `raw` is a ledger row.
